# 알려진 한계

THOTH는 실험 단계의 소스 미리보기입니다. 이 문서는 저장된 결과나 활동 기록이 일부 빠질 수 있는
상황을 정리합니다. **평소 사용에는 영향이 없습니다.** 저장소 오류나 예상 밖의 종료가 특정한
순간에 겹치거나, 지원하지 않는 방식으로 쓸 때만 나타납니다. 항목마다 무엇이 보이는지와
사용자가 할 수 있는 일을 적었습니다. 전체 검증 상태는 [VERIFICATION.md](VERIFICATION.md)에 있습니다.

English: [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md)

## 로컬 모드는 내 컴퓨터의 사용자를 신뢰합니다

로컬 모드는 한 사람이 사용하는 환경을 전제로, 같은 컴퓨터의 프로그램을 별도 인증 없이 신뢰합니다. 서버는 로컬 Host 이름을 확인하고, 상태를 바꿀 수 있는 요청에 Origin이 있으면 로컬 HTTP 출처만 허용합니다. RPC와 취소 요청은 JSON 본문이어야 합니다. 다른 Host·Origin이나 평문 RPC 요청은 거절하며 내장 화면, Vite 개발 프록시, 로컬 JSON 클라이언트는 그대로 사용할 수 있습니다. 이 검사는 인증을 대신하지 않습니다. 같은 컴퓨터의 다른 프로그램은 Origin을 생략하고 허용된 헤더를 보낼 수 있으므로 막지 못합니다. 심사용(hosted review) 모드는 별도 접근 통제를 사용합니다.

## 작업 공간마다 THOTH는 하나만 실행됩니다

작업 공간 하나는 한 번에 THOTH 프로세스 하나만 사용합니다. 같은 작업 공간에서 두 번째를
시작하면 종료 코드 3과 함께 다른 프로세스를 알려 주는 한국어·영어 안내가 나오고, 이미 켜진
서버가 요청을 받으면 기록하지 않고 "작업 공간 사용 중" 오류(HTTP 503)를 돌려줍니다. 다른 THOTH를
닫은 뒤 다시 실행하세요. 이 확인은 로컬 디스크의 운영체제 파일 잠금에 기대므로, Windows와 WSL이
함께 쓰는 폴더나 클라우드 동기화·네트워크 공유로 여러 컴퓨터가 보는 작업 공간은 보호하지 못합니다.
그런 방식으로 같은 작업 공간을 두 곳에서 열지 마세요. 심사용(hosted review) 모드는 이 잠금을 쓰지 않습니다.

## 작업 공간 위치 판정의 한계

로컬 모드는 동기화 폴더·네트워크 공유·Windows/WSL 공유 경로로 확인된 위치를 DB 잠금 전에
막습니다. 판단하지 못한 위치는 명시적으로 확인해야 하며, 이동식 드라이브와 확인한 미분류
위치에는 경고가 남습니다. [위치 조회와 확인 명령](INSTALL.md#workspace-location-policy)을 참고하세요.
`thoth workspace --workspace "경로"`로 확인하고, 미분류 위치를 사용하기로 결정했다면
`thoth accept-location --workspace "경로"`를 실행하세요. `--forget`은 확인 기록만 지웁니다.

Windows 드라이브·클라우드 조회, 파일 속성, 제공자 경로와 동기화 루트 등록 정보를 함께 봅니다.
실제 PC의 읽기 전용 확인에서는 Windows 클라우드 조회만으로 기존 OneDrive 폴더를 잡지 못했고,
알려진 폴더 경로 신호로 차단했습니다. DriveFS의 설정 경로만 있으면 실제 동기화 증거로
단정하지 않고 미분류로 둡니다. 레지스트리 접근 실패도 미분류입니다. 선택적인 등록 키·값이
없으면 그 항목에 등록된 경로가 없는 것으로 봅니다. 모든 동기화 프로그램을 탐지하거나 폴더의
안전을 보증하지는 않습니다. macOS는 현재 미분류이며, Linux는 지정된 mount 종류를 검사합니다.
실제 이동식 디스크·네트워크 마운트·동작 중인 동기화 클라이언트는 집중 주입 시험으로 검증한 것이 아닙니다.

판정과 화면 경고는 저장소를 열 때의 상태입니다. 이후 mount·동기화 설정 변경을 계속 감시하지
않으므로 변경 뒤에는 다시 시작하세요. 확인 기록은 정규화된 작업 공간 식별자와 판정 이유에
묶이며, 알려진 차단 위치를 우회할 수 없습니다. 심사용(hosted review)에는 이 로컬 정책을 적용하지 않습니다.

## 종료로 중단된 요청의 복구

로컬 모드에서는 실측한 67개 명령에 한해, 같은 멱등 key를 다시 보내면 소유 worker의 종료가
확인된 요청을 실패로 닫을 수 있습니다. 같은 호스트·부팅 식별과 이미 보유한 작업 공간 잠금도
필요합니다. `OPERATION_OWNER_GONE`과 함께 저장된 내용을 확인하라는 안내를 반환하며,
handler를 다시 실행하거나 과거 요청을 자동으로 훑어 닫지는 않습니다.

목록 밖의 명령(연구 시작·입력·조정 및 일시정지·재개·중지 포함), 소유 정보가 없는 옛 기록,
호스트 식별이 불명하거나 다른 경우, worker가 살아 있거나 생존 여부가 불명인 경우는
실행 중으로 남을 수 있습니다. 시간 초과만으로 종료를 판단하지 않습니다. 심사용 모드의 복구
정책은 그대로입니다. `improvement/evaluation/run`은 쓰기 없는 응답에 명시적인 unchanged 표시가
없어, 별도 검토 전까지 허용 목록 밖의 후속 후보로 남습니다.

봉인이 원래 완료와의 경합에서 이기면 도메인 변경은 이미 저장됐어도 일반 변경 알림은 빠질 수
있습니다. 새 요청을 보내기 전에 저장된 결과를 확인하세요. 새 질문은 모델 사용량을 다시 쓸 수
있고, 새로 읽은 개정 번호로 보내면 같은 변경이 한 번 더 적용될 수도 있습니다. 이 복구가
외부 효과의 정확히 한 번 실행을 보장하는 것은 아닙니다.

## 같은 요청 재전송으로 빠진 성공 일지를 보충할 수 있습니다

로컬 모드에서는 실측한 20개 명령과 지원되는 저장 결과 형식에 한해, 같은 멱등 key를 다시 보내면
빠진 checkpoint·알림·성공 기록을 채울 수 있습니다. 저장된 결과와 연결 정보는 그대로이며
handler·모델·그 밖의 효과를 다시 실행하지 않습니다. 기록이 다 채워지면 재전송해도 추가하지 않습니다.

새 항목의 시각은 실제 보충 시각이며, `supplemented: true`와 원 완료 시각을 담은
`supplemented_for`가 붙습니다. 기존 항목은 고치지 않습니다. 보충 중 중단되면 그 거래의 새 기록은
함께 취소되고 다음 같은 요청에서 다시 시도할 수 있습니다.

심사용 모드, 실패·진행 중 요청, 연구 게시와 복원 게시에는 적용하지 않습니다. 다른 명령과
확인하지 못한 옛 저장 형식도 보류합니다. 일지 형식이 불명확하거나 서로 충돌하는 경우, 시계 역행
등으로 이벤트 체인의 정렬을 유지할 수 없는 경우, 작업 공간 소유권이 없거나 일시적인 보충 저장
오류가 있는 경우에는 누락이 남을 수 있습니다. 기존 접근 권한 거절과 결과·binding 검증은 유지합니다.

미측정 명령과 추가 source 분기 검토는 후속 작업입니다. 심사용·여러 프로세스 간 보충은 이번 변경
범위 밖입니다. 일지만 고치려고 새 요청으로 다시 보내면 효과가 다시 실행될 수 있으니 저장된 결과를
먼저 확인하세요.

## 샌드박스 연구 시험은 일부만 기록될 수 있습니다

일부 연구 시험은 격리된 샌드박스에서 실행됩니다. 데이터베이스 밖에서 실행한 일은 되돌릴 수
없고, 그 주변의 몇 단계는 따로 저장됩니다.

- 시험 도중 작업 공간이 바뀌면 THOTH는 결과를 버립니다. 결과는 저장되는 순간부터 사용 금지로
  표시되므로 새 근거로 쓰이지 않습니다. 이어지는 두 저장 사이에 앱이 멈추면 "결과를 보류했다"는
  감사 기록 한 건이 빠질 수 있습니다.
- 시험이 실패하고, 실패한 시도를 닫은 뒤 복구 제안을 저장하기 전에 앱이 멈추면 시도는 실패로
  기록되지만 복구 제안이 없을 수 있습니다. 다시 질문하면 보통 새로 만들어집니다.
- 시험이 이미 실행된 뒤 결과 저장이 실패하면 실행은 이미 일어난 일입니다. THOTH는 스스로 다시
  실행하지 않습니다.

## 기준(reference) 단계가 실패해도 연구 답변은 저장되어 있을 수 있습니다

기준 계산 단계가 함께 필요한 질문에서는 연구 답변을 먼저 저장하고 기준 단계를 따로 저장합니다.
기준 단계가 실패하면 오류가 보이지만 연구 답변은 저장된 채로 남습니다. 기준 부분만 다시
질문하세요.

## 메모리 제안은 control record를 두 번에 나눠 저장합니다

메모리 항목을 검증하거나 변경 묶음을 제안하거나 폐기하면 control record를 두 번 저장합니다.
저장소 오류가 나면 두 번째 기록이 빠질 수 있습니다. 남은 기록은 승격과 선택이 읽지 않으므로
잘못된 내용이 쓰이지는 않습니다. 필요하면 제안을 다시 하세요.

## 승인·시도·효과·확인은 독립된 revision이 아니라 연결된 행입니다

승인(authorization envelope), 단계 시도, 효과, 효과 확인(reconciliation), 결과의 하위 기록
(attribution, change set, impact)은 각자의 표에 추가만 되는 행으로 저장됩니다. 각 행은 부모
계획·실행 revision에 연결되고 대부분의 변경은 감사 기록도 남깁니다. 하지만 자기만의 revision
이력, 현재 head, receipt는 없습니다. impact 단계는 감사 기록을 쓰지 않습니다.

실제로는 이렇습니다.

- 승인은 가장 마지막 행을 현재 상태로 읽습니다. 1회용 승인은 하나의 쓰기 거래 안에서 소비되어
  두 요청이 함께 쓸 수 없습니다. 이 규칙은 그 거래와 마지막 revision 확인에 기대고 있으며
  고유 제약 조건은 아닙니다.
- 복원은 새 revision을 만듭니다. 이미 쓴 승인이나 만료된 승인을 되살리지 않으므로 필요하면 다시
  승인하세요. 의도한 동작이지만 처음부터 끝까지 왕복하는 시험은 아직 없습니다.
- 내보내기 묶음이 모든 승인·시도 행을 담는다고 약속하지 않습니다. 작업 공간 데이터베이스 전체
  backup에는 담깁니다.
- receipt는 로컬 기록입니다. 서명하지 않고 로컬 시계를 씁니다.
- THOTH 밖에서 이미 일어난 효과는 THOTH가 되돌릴 수 없습니다. 그 기록이 있다고 외부 시스템이
  실제로 한 일이 증명되지는 않습니다.

## 원자성 검증은 일부만 끝났습니다

기록 영역 열 가지(프로젝트 거버넌스, 자료, 근거, 기준, 판단 대상, 가설, 행동, 실행·결과,
개선, 종료·내보내기)는 일부만 검증된 것으로 표시되어 있고, 검증 문서에는 열린 부채로 나옵니다.
대부분 정상 저장 경로와 여러 실패 지점을 좁은 범위로 시험했지만, 그것은 범위가 한정된 증거이지
완전한 증명이 아닙니다. 위 항목들은 이 작업 중 찾아낸 알려진 틈이고, 다른 틈이 있을 수 있습니다.

## 그 밖의 작은 항목

- 복구 정리가 "닫은 요청 0건"이라고 알려 줘도, 닫을 일이 없었던 것인지 저장소 오류를 잡은 것인지
  구분하지 못합니다.
- 자기 개선 후보의 평가가 실패로 닫히면, 평가 catalog 없는 기존 구성에서는 같은 내용의 후보가
  다시 평가되지 않습니다.
- 마지막 시도가 종료성 실패로 끝난 단계는 스스로 다시 실행되지 않습니다. 사용자가 확인(reconcile)
  하거나 새 revision을 만들 때까지 실행이 기다립니다.
- 파일을 준비하는 업로드 단계에서는 취소할 수 있습니다. 보낸 바이트가 2분 동안 늘지 않으면
  화면에서 요청을 중단합니다. 전송이 끝난 뒤 서버 처리 단계에는 자동 기한이 없고 사용자가
  대기를 취소할 수 있습니다. 진행이 계속되면 전체 시간 제한은 없고, 서버의 64MiB 제한은 그대로입니다. 선택한 파일을 모두 준비한
  뒤에만 자료 연결을 시작합니다. 취소·실패 뒤에도 준비가 끝난 미연결 파일은 inbox에 남을 수
  있지만, 준비만으로 자료 목록이나 근거에 등록되지는 않습니다. 자료 연결은 별도 단계이며
  업로드 취소 버튼으로 취소할 수 없습니다. 실제 배포 환경의 브라우저·프록시 진행 이벤트는
  아직 검증하지 않았습니다. 서버 수신 기한이나 완성된 미연결 파일의 자동 정리는 추가하지 않았습니다.
